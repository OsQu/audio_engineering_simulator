# Luma hardware insert is rejected as a feedback loop

Status: closed — fixed and accepted in the browser (2026-11-08)
Date: 2026-09-09

## Problem

A conventional hardware-insert patch cannot be completed:

```text
DAW return → Scarlett Line Out → Luma Line In
Luma Line Out → Scarlett Line In → USB send / DAW input
```

The first cable connects, but the browser rejects the second with `would create a feedback loop`.
This happens regardless of which cable is connected first.

The patch is safe when Focusrite Control routes a DAW return to the chosen line output and routes the
chosen line input to a USB send. The returned Luma signal is not routed back to its send output, so there
is no active signal-feedback path.

### Root cause

`web/src/connections.ts::wouldCreateCycle` performs cycle detection on a coarse graph where every device
is one vertex. The two external cables therefore reduce to:

```text
Scarlett → Luma → Scarlett
```

At that level, the browser cannot distinguish a correctly routed insert from genuine feedback. It does
not know the Scarlett's internal path:

```text
Line In → AD → digital routing matrix → DA → Line Out
```

The engine has a more accurate node-level graph. Its compiler can keep the schedule acyclic by delaying
a digital edge on such a cycle by one block, which is consistent with a buffered converter/interface
path. A genuinely all-analogue cycle with no digital or acoustic edge remains unbreakable and is rejected.

The browser currently prevents the candidate patch from reaching that authoritative compiler. This is
the broader real-world case of the deferred `docs/IMPROVEMENTS.md` item about making
`wouldCreateCycle` domain-aware.

### Why removing the browser check is not sufficient

Patching currently mutates the authoritative UI scene and then calls `SceneSession.hotSwap()`. The new
patch is sent asynchronously to the AudioWorklet. If `SceneEngine::load_patch` rejects it, the worklet
keeps the previous runnable engine, but the invalid connection remains in the UI scene and its persisted
URL state. The page and audio engine can therefore disagree.

The browser also lacks enough catalog metadata to reproduce the compiler's decision exactly. Exposed
port domain, connector, direction, and channel count do not describe internal port-to-port reachability,
converter boundaries, or delay-eligible paths. Inferring safety from the presence of digital ports would
be unreliable, and a Scarlett-specific exception would violate the generic catalog/engine boundary.

## Proposed solution

Make structural patch validation engine-authoritative and transactional.

### Transaction

1. Apply the proposed cable edit to a candidate patch, leaving the authoritative `Scene` unchanged.
2. Send `loadPatch` to the AudioWorklet with a monotonically increasing request ID.
3. Let the existing Rust `build_patch` and `compile` pipeline validate and build the candidate.
4. On success, the worklet replies with `patchAccepted { requestId, ... }`; commit the candidate to the
   UI scene, seed its parameter state, and let the queued schedule become live at the next block boundary.
5. On failure, the worklet replies with `patchRejected { requestId, message }`; discard the candidate,
   keep the previous UI scene and running schedule, and show the compiler's error to the user.
6. Ignore stale acknowledgements by request ID, or allow only one structural transaction at a time.

This makes the Rust compiler the single topology oracle and prevents the scene from diverging from the
running engine.

### Browser preflight after the change

Keep immediate client-side checks that are exact from published port metadata:

- output-to-input direction;
- carrier-domain compatibility;
- connector compatibility, including catalog-backed adapter cables;
- digital channel count;
- duplicate connections and occupied-input replacement;
- connecting a device directly to itself.

Remove the coarse multi-device `wouldCreateCycle` rejection. Cycles involving internal routing or
converter boundaries must be submitted as candidates to the engine. The engine accepts cycles it can
break at a physically eligible digital/acoustic edge and rejects unbreakable all-analogue feedback.

### Expected code areas

- `web/src/connections.ts` — stop treating a device-level cycle as a final connection verdict.
- `web/src/scene-ops.ts` — produce/apply candidate connection edits without prematurely mutating the live
  scene.
- `web/src/patch-controller.svelte.ts` and `web/src/session.svelte.ts` — own the pending transaction and
  commit or discard it after acknowledgement.
- `web/src/engine.ts` and the AudioWorklet source — add request IDs and accepted/rejected responses for
  `loadPatch`.
- Rust `build_patch` / `compile` — remain authoritative; no device-specific exception should be needed.

Publishing complete internal reachability and delay metadata through `PortDescriptor` is an alternative,
but it would duplicate engine topology in the UI and must track runtime routing matrices. It is larger
and more fragile than transactional engine validation.

## Acceptance criteria

1. The following two-cable patch is accepted and survives save/reload:

   ```text
   Scarlett Line Out 3 → Luma Line In
   Luma Line Out → Scarlett Line In 3
   ```

2. With the Scarlett matrix routed as a hardware insert, audio travels through the Luma and returns to a
   USB send without uncontrolled feedback.
3. The compiler's bounded-latency cycle break is present on a digital edge; cable R·C and balanced-line
   behavior remain intact on both analogue connections.
4. A deliberately unbreakable all-analogue feedback loop is rejected, remains absent from the UI scene,
   and does not replace or interrupt the previously running schedule.
5. A rejected candidate produces a clear user-facing error and does not enter URL-persisted scene state.
6. Rapid or overlapping structural edits cannot commit an acknowledgement for an obsolete candidate.
7. Existing direction, domain, connector, adapter-cable, channel-count, fan-in replacement, duplex USB,
   and hot-swap tests remain green.

## Resolution (2026-09-11)

The patching path now uses the proposed engine-authoritative transaction. `evaluateConnection` retains
only metadata checks and no longer rejects a coarse device-level cycle. `PatchController` edits a
detached scene snapshot, then `SceneSession` sends it as one request-ID-tagged `loadPatch` candidate.
The AudioWorklet responds with `patchAccepted` or `patchRejected`: acceptance commits that exact
snapshot; rejection preserves the prior scene and reports the compiler error in the status line. One
candidate is permitted at a time, and unmatched acknowledgements are ignored.

This specifically unblocks the Scarlett → Luma → Scarlett insert while retaining engine rejection for
unbreakable all-analogue cycles. The focused browser unit test and type check pass. The representative
interactive patch/audio verification in criteria 1–3 remains to be performed in the workbench.

## Acceptance (2026-11-08)

Run in the studio view against the live dev server (real AudioWorklet, headless Chromium driven by
Playwright). Starting scene: the default monitoring loop plus an unpatched Luma (powered), the 8i6
rear panel turned to face the operator, and one extra 8i6 crosspoint, DAW return 1 → Line Out 3, so the
DAW return also feeds the insert. The identity matrix already routes Line In 3 → USB send 3.

1. **Accepted and persisted.** Both cables were patched with the normal jack click-click gesture:
   Scarlett Line Out 3 → Luma Line In, then Luma Line Out → Scarlett Line In 3. Both were accepted,
   with no feedback-loop rejection, and the catalog's `balanced_trs_xlr_3m` adapter lead was resolved
   for each. After **⚙ Scene → save** and a full page reload, both cables were in the saved scene and
   drawn again.
2. **Audio through the Luma, no runaway.** While a held note played (the controller's focus window
   with a computer-keyboard note), the computer's meters read USB send 1 at 0.0 dBFS peak (the dry
   recording) and USB send 3 at −1.1 to −2.1 dBFS peak (the insert's return). The send 3 level stayed
   steady and dropped to silence (—) on note release, so nothing kept circulating. With the Luma's
   Power switched off, send 3 stayed silent while send 1 kept reading 0.0 dBFS. With it back on, send 3
   came back (−1.3 dBFS). So the returning signal really passes through the Luma. Debug health
   reported 0 overruns across ~35k quanta.
3. **Digital cycle break; analogue cables intact.** The new `build_patch` test
   `luma_hardware_insert_builds_and_passes_signal_through_the_luma` builds the same two-cable insert
   with no device-specific exception. The only breakable edges on that cycle are digital, inside the
   interface. Both insert cables keep their hand-calculated resistive loading: −1.940 dB from the 150 Ω
   DA into 600 Ω, and −0.118 dB from 600 Ω into the 44 kΩ balanced receiver. A note routed
   Pre 1 → Line Out 3 → Luma → Line In 3 → Line Out 4 arrives only while the Luma is powered.

Criteria 4–7 are covered by the transactional seam's existing tests. The real-worklet browser spec
`worklet-patch-acceptance.spec.ts` checks that a rejected candidate is never installed and that a
protocol mismatch fails closed. The web unit suite covers the rest. All of these pass on this branch.
